# ADR-001: Untrusted Controller Execution and MicroVM Hardware Isolation

- **Status:** Accepted
- **Date:** 2026-11-05
- **Deciders:** Lead Engineering Architect, Security Working Group
- **Consulted:** Vultr Serverless Inference Team, Forseti Simulation Team

---

## Section 1: Context and Problem Statement

Dómnir evaluates autonomous flight controllers generated by large language models (LLMs) and user submissions for the Bitcraze Crazyflie 2.0 quadrotor. Because generated controller code is untrusted arbitrary Python, running it directly on the host process presents severe security and physical containment risks:
- Host filesystem, process, network, and environment compromise.
- Host secret leakage (e.g., Vultr API keys, operator tokens, signing keys).
- Mutation or corruption of the trusted MuJoCo simulation model or state.
- Host denial of service through unbounded loops, memory exhaustion, or thread starvation.

We require a containment architecture that achieves **Blast Radius Zero**: even if an untrusted controller attempts hostile system calls, network egress, file exfiltration, or host socket access, the host and other tenants remain completely unharmed.

---

## Section 2: Vultr Serverless Inference & Zero Host Credential Bleed

All autonomous controller synthesis, diagnostic reasoning, and CEGIS repair queries are routed through Vultr Serverless Inference at `https://api.vultrinference.com/v1`.

### Credential Isolation Guarantees
1. **Server-Side Only:** Vultr API keys (`VULTR_API_KEY`) reside exclusively in backend environment memory on the control plane VM.
2. **Zero Client Bleed:** API keys and raw provider credentials are never transmitted to the browser client or included in public web bundles.
3. **Zero Guest Bleed:** API keys are never mounted, injected, or accessible inside the guest execution sandbox.
4. **Model Pinned Catalog:** Controller generation targets pinned, verified models (such as `glm-5.3-flash`, `qwen-3.8-flash-next`, and `deepseek-v4.1-flash`) with strict token and budget boundaries. No silent fallback to third-party providers is permitted.

---

## Section 3: Blast Radius Zero: Hardware MicroVM Containment Architecture

Guest controller execution occurs strictly inside dedicated Microsandbox microVMs backed by AMD EPYC nested KVM hardware virtualization (`/dev/kvm`).

### MicroVM Containment Invariants
1. **Hardware Boundary:** Every untrusted controller runs inside an ephemeral Linux microVM instance. Container-only or unvirtualized host execution is strictly prohibited in production.
2. **Zero Host Mounts:** No host filesystem directories, Docker sockets, or devices are mounted into the microVM.
3. **Default-Deny Networking:** MicroVM network interfaces are configured default-deny. All outbound egress and inbound ingress traffic is dropped.
4. **Rigid Resource Limits:**
   - Monotonic wall-clock watchdog ceiling: 0.50 s per step.
   - Memory allocation limit: 256 MiB.
   - CPU quota: 1 dedicated vCPU.
   - Frame payload ceiling: 32 KiB maximum controller source size.
5. **State Ownership Boundary:** The host simulator (Forseti) alone owns and mutates the trusted MuJoCo model and `MjData`. The guest microVM only receives observation frames and returns requested rotor thrust vectors.
6. **Mandatory Lifecycle Teardown:** Every sandbox lease is bound to a strict context manager that guarantees 100% reclamation and cleanup upon exit, crash, timeout, or cancellation.

---

## Section 4: Consequences and Invariants

- **Fail-Closed on Unvirtualized Hosts:** If `/dev/kvm` or Microsandbox is absent on a production host, execution fails closed with status `UNAVAILABLE`. Subprocess execution is strictly limited to isolated local development test suites and explicitly blocked in production.
- **Independent Replay:** Simulation results, actions, and observations recorded during execution are sealed into canonical Court Records. Physical replay can be deterministically re-evaluated on any trusted host without re-executing untrusted controller code.
- **Auditable Proof:** Containment guarantees are continuously verified by the automated containment audit suite (`CAP-HOST-001`, `FS-HOST-001`, `NET-EGRESS-001`, `TIMING-001`, `WATCHDOG-001`) with evidence archived under `docs/evidence/`.
