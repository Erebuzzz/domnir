# Feasibility status

The implementation plan defines three gates: a KVM-backed microVM, a persistent host-to-guest control channel, and a calibrated Crazyflie baseline. The first two have limited feasibility evidence below. The calibration gate remains open.

## Vultr sandbox and channel spike

On 5 November, the Ubuntu 24.04 VX1 host exposed `svm` and `/dev/kvm`. Microsandbox 0.7.13 `doctor` reported KVM read/write access. A `python:3.12-slim` guest booted with 1 CPU and 512 MiB, which `msb status` reported. Host-side inspection showed default-deny ingress and egress rules, no published ports, and no mounts. A fixed guest fixture reported that it could not see a host-only canary or connect to one public TCP address. These guest reports are untrusted observations, not a complete network audit or host-side per-attempt denial event.

The guest image resolved to `sha256:1148dbb014615300fa7e713b2f94f550c0d1c69780c0805f84f093ceee34dd0b`. A persistent `msb exec --stream` channel exchanged 1,000 sequential fixed JSON echo frames with no missed frames: p50 0.75 ms, p95 0.92 ms, and maximum 58.95 ms on that run. This is a simple fixture, not controller execution under a real-time deadline. Stopping and removing that sandbox succeeded. A separate sandbox configured with a 15-second maximum duration was observed stopped after the deadline and then removed. No sandboxes remained in the runtime after cleanup. CPU and memory values were inspected, but exhaustion and enforcement under load were not tested.

The lifecycle adapter pins runtime 0.7.13 and the observed image digest, creates a guest with default-deny network policy and a maximum duration, checks the reported active configuration, and removes it on context exit. A command-line path accepts a bounded single-file Python controller, validates UTF-8, syntax, and a top-level `observe` definition, and copies it into the guest without a host mount. Parsing does not prove the source is safe. The guest imports and invokes the controller; the trusted host bounds frames and per-step response time, checks actions, advances MuJoCo, records the source and runner hashes, and replays the actions. This is not yet a public upload service or a production-ready execution boundary.

The [Vultr Microsandbox guide](https://docs.vultr.com/how-to-set-up-agent-sandboxing-on-vultr-cloud-compute) documents the KVM requirement and runtime setup. The [upstream command documentation](https://github.com/superradcompany/microsandbox/blob/main/docs/sandboxes/commands.mdx) describes the dedicated guest command channel.

## Local simulation spike

The Menagerie Crazyflie model states that its actuator limits are arbitrary. A local stationary hover and action replay are a model-loading and determinism check only. The check does not validate the limits, physical fidelity, obstacle flight, or deployed runtime. Pin and verify the model, simulator, assets, and environment for any result intended as evidence.

On 5 November 2026, MuJoCo 3.3.7 on Windows loaded Menagerie commit `98a70c569c4c1b6da467a20012f766ee1f8dc521`. For a level start 0.05 m above the target, a simple altitude controller ran for 1,000 steps at 0.002 seconds. The final altitude error was approximately -0.00326 m, and replaying the captured actions in a separately loaded model produced zero maximum absolute state difference on the same machine. This single case is not a calibrated flight controller or evidence of general reproducibility.

The same altitude case produced the same reported final error and zero replay difference on the Vultr host. A trusted simulation kernel validates bounded action frames and independently replays a captured action sequence. Both a fixed fixture and a supplied controller exchange observations and actions with that kernel using a bounded, deadline-controlled stream. This is not a product verdict system. Menagerie's actuator ranges remain untuned, so the physical calibration gate is still open.

The [controller trial](evidence/controller-trial-20261105.json) records a supplied example controller's 200-step Vultr run, trusted states and actions, replay, source and guest-runner hashes, and successful cleanup. The maximum observed round trip includes startup latency. This single example does not establish performance or safety for other controllers.

The [controller campaign](evidence/controller-campaign-state-v2.json) ran eight synthetic scenarios on Vultr using seed 42: a baseline, three fixed edge cases, and four seeded random cases. Five crossed the declared 0.05 m altitude limit; all eight action replays matched within the 1e-12 tolerance. The record separately marks flight qualification `INCONCLUSIVE`, containment `NOT_TESTED`, and provenance `INCOMPLETE`. Its [host event log](evidence/controller-campaign-state-v2.json.events.jsonl) has 26 hash-linked events and was checked for consistency with the campaign. It is unsigned; a party able to rewrite both log and reference can recompute them. It is a feasibility record, not a tamper-proof Court Record. The [calibration status](MODEL_CALIBRATION.md) explains why the plant gate remains open.

The `feasibility-2` record captures MuJoCo `mjSTATE_INTEGRATION` at each step, including initial integration state, alongside controls and disturbances. On the same Vultr environment, a separate verifier restored the saved initial state and re-ran the recorded actions and forces without starting the controller; all eight full integration traces matched with maximum absolute difference zero. This is evidence for the pinned model and environment, not a guarantee for different models, simulator versions, architectures, plugins, or external callbacks. Earlier `feasibility-1` records are retained as historical evidence and do not contain the full integration snapshots.

On 5 November, a four-case, fixed synthetic sweep varied initial altitude between 0.10 and 0.15 m and vertical force between 0 and -0.05 N. With a 0.05 m test altitude limit, the worst case reached approximately 0.00348 m and replayed with zero maximum state difference on the same host. The full [fixture evidence](evidence/fixture-search-20261105.json) records the four scenarios, state/action/replay traces, hashes, and cleanup results. The host model hashes match the raw Git blobs at the pinned Menagerie commit. A Windows checkout may have different raw hashes because of line-ending conversion. These are synthetic findings, not physical flight results.
